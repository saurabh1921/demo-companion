Boomi · Zendesk · Magento — Cutover Runbook

Taking the order status API from demo to live

Everything currently deployed works end to end, but against mock data behind a Demo Mode switch. This is the exact set of changes that replaces the mocks with a real Magento store — what is configuration, what is code, and what is genuinely unfinished.

What makes it a demo right now

Six things, in descending order of how much work they are:

#WhatEffort
1Magento base URL is a placeholder host that does not resolveConfig
2Bearer token is the literal string REPLACE_WITH_…Config
3DPP_DEMO_MODE is true, so both lookups hit Message-step mocks instead of the REST callsConfig
4Demo scaffolding on the canvas — mock steps, a standalone test harness, a Notify that logs the full customer payloadSmall code change
5Tracking number and carrier are modelled on a field real Magento does not return thereReal code change
6Nothing has ever run against a real Magento order documentTesting

Minimum to see real data

Steps 1–4. Roughly half a day, mostly waiting on Magento credentials. You get live orders in the chat window, without tracking numbers.

Production ready

All eleven steps. Adds the shipments lookup, PII handling, a production runtime, and the Zendesk-side integration that this prototype fakes with a local proxy.

01

Create a Magento integration and get a tokenBlocking

Magento admin

In the Magento admin: System → Extensions → Integrations → Add New Integration.

  1. Name it something traceable, e.g. Boomi Order Status Bot.
  2. On the API tab set Resource Access to Custom and tick Sales → Operations → Orders. If you are doing step 06 as well, also tick Sales → Operations → Shipments.
  3. Save, then Activate the integration from the grid and approve it.
  4. Copy the Access Token. That single value is what Boomi sends as Authorization: Bearer <token>.
Use an integration token, not an admin token

Magento also issues tokens from POST /rest/V1/integration/admin/token, but those expire (4 hours by default) and would need refresh logic Boomi does not currently have. Integration access tokens do not expire, which is why the connection is built around one.

Grant read-only order access and nothing else. This token can list every order in the store, so treat it as a production secret.

03

Put the token into both operationsRequired

Boomi

The same edit in two places — the operations do not share a header.

GET Magento Order by Increment ID — edc08219-420d-4fb5-9023-837d869c1f1d
GET Magento Orders by Customer Email (3 Most Recent) — d5c34b3c-46d5-494d-a5a8-894d7faf3391
NowAuthorization: Bearer REPLACE_WITH_MAGENTO_INTEGRATION_ACCESS_TOKEN
Change toAuthorization: Bearer <access token from step 01>
Set this one in the Boomi UI, then encrypt it

Paste the token in the operation's Request Headers, then use the UI's encrypt control on that header. Do not commit the real token to the XML in this repo — the placeholder is there so the component can be version-controlled without a secret in it.

Nothing else about the operations changes. The searchCriteria parameters are already correct for Magento's order search: filter on increment_id or customer_email, sorted created_at DESC, pageSize 1 and 3 respectively. The filter value is bound at the step from DDP_ORDER_ID / DDP_EMAIL and needs no change.

04

Turn off demo modeRequired

Boomi

In [SUB] Magento Order Status Lookup, the Set Demo Mode Flag step near the start controls which way both lookups branch.

Subprocess → Set Demo Mode Flag → DPP_DEMO_MODE
Nowtrue → Message-step mocks
Change tofalse → real REST calls

That one value is the whole switch. Both Demo Mode? decisions then route to Clear Document Before GET → the REST connector instead of the mock.

This cannot be an environment extension as built

The obvious instinct is to expose DPP_DEMO_MODE as an environment extension so test and production can differ. That will not work while the Set Properties step exists: a step that explicitly sets a DPP overwrites any extension-injected value for the rest of the execution. To make it environment-driven you must delete the Set Properties step first — at which point you may as well do step 05 and remove the branch entirely.

Keep Log Magento Failure (Internal Only). It logs the exception detail and the request context at SEVERE while the customer still gets the generic message — that separation is the point, and it is your only diagnostic on the failure path once payload logging is gone.

06

Fix tracking — it will silently come back emptyCode change

Boomi

This is the one place where the demo made an assumption that real Magento does not satisfy, and it fails quietly rather than loudly.

The profile j.Magento.OrderSearch.RESP reads tracking from items[].extension_attributes.tracking_number and .carrier_title. A stock Magento /V1/orders search does not return those fields. Tracking lives on shipments, not orders. The map will simply find nothing, omit both keys, and every order will render without a tracking block — no error anywhere.

Three ways out

  1. Second call to /V1/shipments. Filter on order_id — note that is Magento's numeric entity_id, not the increment_id the customer quotes, so add entity_id to the order profile first. Read items[].tracks[].track_number and .title, then join back with a Document Cache keyed on order id.
  2. Have Magento expose it. If you have developers on the store, a custom extension attribute surfacing tracks on the order endpoint keeps Boomi at one call per lookup. Cheapest option at runtime, needs a Magento release.
  3. Ship without tracking for now. Genuinely viable: the widget already handles a missing tracking block cleanly — one of the demo orders has no tracking and renders correctly. The bot just cannot answer "where is it".
Also verify line items against a configurable product

Magento returns configurable products as two rows in items[] — the configurable parent and its simple child. The map does not distinguish them, so such an order may show each item twice in the chat window. Test with a real configurable-product order before launch; if you see duplicates, add parent_item_id to the profile and filter the rows where it is populated.

07

Make the endpoint environment-configurableRecommended

Boomi

Right now the Magento URL and token are baked into the components, so a staging store and a production store would need two copies. Neither process declares <bns:processOverrides> yet. Add one to the subprocess — it owns the connector steps:

<bns:processOverrides>
  <Overrides xmlns="">
    <Connections>
      <ConnectionOverride id="362a16cc-a38e-44f7-a0ad-98fa8197369d">
        <field id="url" label="Magento Base URL" overrideable="true"/>
      </ConnectionOverride>
    </Connections>
  </Overrides>
</bns:processOverrides>

Then set the per-environment value through the Environment Extensions API and confirm it surfaced:

# read what is currently overrideable in an environment
GET /api/rest/v1/{accountId}/EnvironmentExtensions/{environmentId}
Never push an empty processOverrides element

Deploying a process with <bns:processOverrides/> or an empty <Overrides/> deletes that process's extension declarations from the environment, discarding values already set through the API. Either declare the full block or omit the element entirely.

08

Decide how much customer data you keepRequired

Boomi · Privacy

The demo is deliberately transparent, which is the wrong default for real orders.

  • Payload logging. Log Outgoing Chat Payload writes every customer's order history, totals and tracking numbers into the process log. Remove it (step 05).
  • Document retention. Both processes run with purgeDataImmediately="false", so request and response documents persist for troubleshooting. For real customer data, consider setting it true on the wrapper — you lose payload-level debugging in exchange for not retaining PII.
  • Retry on the connector. The try/catch is set to retryCount="0". One or two retries would absorb transient network blips before the customer sees the "temporarily unable" message. Do not go higher — every retry re-runs the whole try path.
09

Deploy to a production runtimeRequired

Boomi ops

Everything is currently deployed to the test environment fa239dee-b397-45a6-8cff-89e659f64a22 on atom f02b49c7-7cb6-420f-b645-f57e32fe4d1f.

Atom type is not a free choice here

This is a plain Web Services Server listener with no API Service component wrapping it. That pattern deploys to Basic or Intermediate atoms only — it will not serve traffic from an Advanced atom. If production is an Advanced runtime, the process has to be wrapped in an API Service component first, which is a different build.

Deploy order matters — the parent snapshots the subprocess at deploy time, so the subprocess goes first and the parent second, always:

bash scripts/boomi-deploy.sh active-development/processes/SUB_Magento_Order_Status_Lookup.xml
bash scripts/boomi-deploy.sh active-development/processes/API_Zendesk_Order_Status.xml

Then allow 10–15 seconds before the first request. Executing sooner runs the previous package and will look like your change did not take.

On the production atom, configure the Shared Web Server: enable it, set authentication to Basic (or client certificate), install a real TLS certificate, and note the base URL. The endpoint path is unchanged:

POST https://<prod-atom-host>/ws/simple/queryZendeskOrderStatus
10

Connect Zendesk for realBlocking

Zendesk admin

The prototype's server.py stands in for this. It is a development proxy — a single-threaded Python HTTPServer with no TLS, rate limiting, or error budget. It must not go to production.

Credentials cannot live in the browser

The Boomi shared web server expects Basic auth. Anything running in the customer's browser — including the Zendesk Web Widget — would expose those credentials to anyone who opens developer tools. The call has to be made server-side.

Which route depends on your Zendesk plan:

  • Zendesk bot builder with an API call step — the bot calls the Boomi endpoint directly and holds the auth header in Zendesk's config. Simplest when your plan includes it.
  • Sunshine Conversations webhook — Zendesk posts to your own service, which adds auth and forwards to Boomi. More moving parts, more control.
  • A small internal API service — the same shape as server.py but production-grade, if you already run one.

Whichever you pick, the contract does not change. The bot collects an order number or an email and posts:

{
  "request_type":    "order_status",
  "email":           "",
  "order_id":        "000000498",
  "conversation_id": "zd-88421"
}

Send one or the other. Order number wins if both are present. Send neither and the API returns a polite prompt for more detail rather than an error, which the bot can show verbatim.

11

Verify against real ordersRequired

Whoever cuts over

Pull three real order numbers from the store first — one shipped, one still processing, one cancelled or closed — plus a customer email with more than three orders.

  • Known order number returns that order, with the correct total and line items
  • Email returns exactly three orders, newest first — proves pageSize and the sort survived
  • Customer with a configurable-product order shows each item once (see step 06)
  • Shipped order shows a tracking number, or you have accepted option 3 in step 06
  • Order number that does not exist returns not_found, not an error
  • Email with no orders returns not_found
  • Empty request returns the "need more info" prompt
  • Wrong token returns the generic unavailable message, and the real cause appears in the Boomi log at SEVERE
  • Magento unreachable behaves the same way, and the process still completes rather than erroring
  • Several requests at once all succeed

The last four matter most. They are the difference between an outage the bot absorbs gracefully and one that shows a stack trace to a customer.

Two testing traps already hit on this build

macOS curl fails against the Boomi shared web server at the TLS layer even with -k; it is a local LibreSSL problem, not an unreachable endpoint. Test with Python requests/urllib or Postman instead. Separately, a test execution returning DISCARDED means a previous run of the same process was still active — it is a concurrency gate, not a failure.
