01 · Overview
Solution Summary

This integration exposes a synchronous REST API endpoint using Boomi's Web Services Server (WSS). Incoming order payloads are enriched via an external API call, transformed to a canonical target schema, and simultaneously dispatched to three downstream channels — all within a single, fault-tolerant execution.

What This Integration Does

Receive Order via REST API
WSS Listener accepts POST /ws/simple/createOrder with JSON order payload
Enrich Customer Data
Calls JSONPlaceholder /users/{customerId} to fetch name, email, and company
Transform to Target Schema
Map merges order data (via DPPs) + enrichment into canonical OrderIntake_Target format
Fan-Out to 3 Channels
Branch step delivers to Warehouse DB, Event Streams topic, and returns HTTP 200 with acceptance receipt
⚡

Key Integration Patterns

WSS Wrapper + Subprocess
Thin API wrapper delegates to a thick, independently testable subprocess — clean separation of concerns.
DPP-Bridged Enrichment
Dynamic Process Properties (DPPs) preserve original order fields across the REST enrichment call boundary.
Multi-Target Branch Fan-Out
Branch step distributes one mapped document to three channels simultaneously, with independent error isolation per path.
Try/Catch Error Envelope
Entire business logic wrapped in try/catch — errors produce structured JSON error responses, never silent failures.

04 · API Reference
REST Endpoint

The integration exposes a single synchronous REST endpoint via Boomi's Shared Web Server on MyMacAtom.

POST http://localhost:9090/ws/simple/createOrder
URL Pattern — Boomi WSS path is constructed as: lowercase(operationType) + SentenceCase(objectName)
operationType="CREATE" + objectName="order" → /ws/simple/createOrder

Request Body

application/json 
{
  "orderId":     "ORD-20260408-001",
  "customerId":  "3",
  "orderType":   "standard",
  "callbackUrl": "https://example.com/callbacks",
  "totalAmount": 249.99,
  "currency":    "USD",
  "items": [
    {
      "sku":      "SKU-A100",
      "quantity": 2,
      "price":    99.99
    }
  ]
}

Response · HTTP 200

application/json · 200 Accepted 
{
  "status":  "accepted",
  "message": "Order received and
             processing initiated",
  "orderId": "ORD-20260408-001"
}

Response · HTTP 500 (Error)

application/json · error path 
{
  "status":  "error",
  "error":   "ProcessingException",
  "message": "<boomi error detail>"
}

Map Transformation Logic

The map component OrderIntake_Enrich_To_Target_Map combines live enrichment profile data with DPP-preserved order fields to produce the canonical target document.

📥

FieldKeyMaps To
namekey 4customerName
emailkey 5customerEmail
company.namekey 9companyName
ℹ️ Source profile represents the current document after the REST enrichment call to JSONPlaceholder.
⚙️

Map Functions: DPP Injection (7 functions)

FunctionDPP NameTarget Field
fn1: PropertyGetDPP_ORDER_IDorderId
fn2: PropertyGetDPP_CUSTOMER_IDcustomerId
fn3: PropertyGetDPP_ORDER_TYPEorderType
fn4: PropertyGetDPP_TOTAL_AMOUNTtotalAmount
fn5: PropertyGetDPP_CURRENCYcurrency
fn6: PropertyGetDPP_CALLBACK_URLcallbackUrl
fn7: CurrentDate—processedAt
🔑 Why DPPs? — When the REST connector executes, it outputs a new document (the enrichment response), discarding DDPs attached to the original order document. Dynamic Process Properties (DPPs) are process-scoped and survive across connector boundaries, making them the correct mechanism to bridge the original order fields into the post-enrichment map.
