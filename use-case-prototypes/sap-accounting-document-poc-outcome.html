What the data told us

The extracts repeat themselves — most records are documents we have already seen

10,353records in API_API0017 (11.6 MB, 8–10 Jul 2025)
2,223genuinely distinct accounting documents
4.7×average repetition — the same document re-appears in later extracts
Why this drove the design Posting every record as it arrives would have created roughly 8,130 duplicate financial documents. Deduplication is therefore not a refinement — it is the core of the solution, and it is what the POC was built to prove.
04

What we built

One Boomi process, from extract to posted SAP document

1 · readCollect extract

Picks up the file with no manual step

2 · parseSplit records

Separates the run-together JSON into individual documents

3 · protectCheck if posted

Compares against a durable ledger of everything posted before

4 · transformMap to SAP

Builds the accounting-document structure SAP expects

5 · postPost & confirm

Writes to SAP and reads back its confirmation

6 · reportSummarise run

Posted, skipped and errored, per run

The ledger is only updated after SAP confirms a document was created — so a failed posting is never recorded as done, and is retried on the next run rather than being lost.

06

Cases handled

Four failure modes are handled explicitly, not left to chance

  • 01Document already posted in a previous run. Recognised against the ledger and skipped. No SAP call is made.
  • 02Document repeated twice inside the same file. Caught within the batch — the second occurrence is skipped even though the first only posted moments earlier.
  • 03SAP rejects a posting. The rejection reason is captured, the document is quarantined, and it is deliberately not written to the ledger so the next run retries it.
  • 04A record is corrupt. Quarantined individually with its reason. The remaining records in the same file continue to post normally.

Each of the four was demonstrated in a live run against SAP, not designed on paper.

Next steps

Three things turn this demonstration into a production integration

  • 01Point it at an Abans SAP environment. Company code, chart of accounts, document type and posting periods become the real ones, and the account translation table is no longer needed. Configuration, not development
  • 02Confirm what the existing ABAP program does beyond posting. If it applies derivations or validations of its own, those must be reproduced — this is the one open question that could change the design. Needs Abans SAP team
  • 03Extend to the remaining extracts and full volume. Add the customer and vendor line types, cover API0018 and API0023 including its mixed record shapes, and move the duplicate ledger to a database for parallel posting. Scoped extension

The mechanism is proven. What remains is configuration, one clarification, and a defined extension — not further proof of concept.
