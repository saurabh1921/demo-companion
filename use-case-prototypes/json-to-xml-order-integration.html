2Business Context / Konteks Bisnis

🇬🇧 EN

The Problem. Most enterprises run a mix of modern (REST/JSON) and legacy (XML/SOAP/EDI) systems. Order data arriving from a customer-facing app must be reshaped before a legacy ERP can accept it. The two formats describe the same data, but the structure differs.

Modern Channel (JSON)Legacy ERP (XML)
Flat object with arraysNested elements with repeating blocks
Camel-case field names (customerName)Pascal-case wrapped (Customer > Name)
Numbers as primitivesNumbers as element text
Metadata mixed with itemsStrict header / customer / items / footer hierarchy

The Risk of Not Solving It Cleanly:

  • Hand-coded transformers become a single-developer dependency, hard to audit, brittle when payloads evolve.
  • Point-to-point integrations explode in count as more channels and ERPs are added (N × M problem).
  • No central visibility means business teams can't see where an order is, what failed, or why.

The Boomi Approach. A declarative, profile-driven transformation that any moderately trained developer can read, modify, and extend. Hosted on a managed runtime. Auditable. Versioned. Promotable across Dev → Test → Prod through configuration alone.

🇮🇩 ID

Masalahnya. Sebagian besar perusahaan menjalankan campuran sistem modern (REST/JSON) dan legacy (XML/SOAP/EDI). Data pesanan yang masuk dari aplikasi pelanggan harus diubah bentuknya sebelum dapat diterima ERP legacy. Kedua format menjelaskan data yang sama, tetapi strukturnya berbeda.

Saluran Modern (JSON)ERP Legacy (XML)
Objek datar dengan arrayElemen bersarang dengan blok berulang
Nama field camel-case (customerName)Pascal-case bersarang (Customer > Name)
Angka sebagai primitifAngka sebagai teks elemen
Metadata tercampur dengan itemHirarki ketat: header / customer / items / footer

Risiko Jika Tidak Diselesaikan dengan Baik:

  • Transformator yang ditulis tangan menjadi ketergantungan pada satu developer, sulit diaudit, rapuh saat payload berubah.
  • Integrasi titik-ke-titik bertambah eksponensial saat ada lebih banyak saluran dan ERP (masalah N × M).
  • Tanpa visibilitas terpusat, tim bisnis tidak dapat melihat di mana pesanan berada, apa yang gagal, atau mengapa.

Pendekatan Boomi. Transformasi deklaratif berbasis profil yang dapat dibaca, dimodifikasi, dan diperluas oleh developer dengan keterampilan menengah. Berjalan pada runtime terkelola. Dapat diaudit. Terversi. Dapat dipromosikan Dev → Test → Prod hanya melalui konfigurasi.

6How It Works — Deep Dive / Penjelasan Cara Kerja

Concept 1 — Profiles Are Contracts / Konsep 1 — Profil Adalah Kontrak

🇬🇧 EN

A profile is Boomi's name for a schema. It defines the shape of data: which fields exist, their type, what's optional, what repeats. Two profiles were defined: j.NTTDemo.Order.REQ (JSON) and x.NTTDemo.Order.ERP (XML). Profiles are reusable across processes.

🇮🇩 ID

Sebuah profil adalah nama Boomi untuk skema. Profil mendefinisikan bentuk data: field apa saja, tipenya, mana opsional, mana berulang. Dua profil didefinisikan: j.NTTDemo.Order.REQ (JSON) dan x.NTTDemo.Order.ERP (XML). Profil dapat dipakai ulang lintas proses.

This is the single most important takeaway. Hand-coded transformations require explicit for loops, array index management, and null checks. Boomi infers all of that from the profiles. Less code = fewer bugs = faster delivery.

🇮🇩 ID

Inilah poin terpenting. Transformasi yang ditulis tangan memerlukan loop for eksplisit, manajemen indeks array, dan pemeriksaan null. Boomi menyimpulkan semuanya dari profil. Lebih sedikit kode = lebih sedikit bug = pengiriman lebih cepat.

Concept 3 — Documents Flow / Konsep 3 — Dokumen Mengalir

🇬🇧 EN

Boomi models data as a stream of documents flowing left-to-right through shapes. Each shape passes them through, transforms, replaces, or terminates them. This pipeline model matches modern data-engineering thinking.

🇮🇩 ID

Boomi memodelkan data sebagai aliran dokumen dari kiri ke kanan melalui shape. Setiap shape meneruskan, mentransformasi, mengganti, atau menghentikan dokumen. Model pipeline ini sesuai cara pikir data engineer modern.

Concept 4 — Repeating Elements Are Declared / Konsep 4 — Elemen Berulang Dideklarasikan

🇬🇧 EN

In both profiles, array/repeating structures are flagged with maxOccurs="-1" (unbounded). This single attribute tells Boomi: "there can be many of these — iterate." No explicit loop is ever written.

🇮🇩 ID

Pada kedua profil, struktur berulang ditandai maxOccurs="-1" (tak terbatas). Atribut tunggal ini memberitahu Boomi: "bisa ada banyak — lakukan iterasi." Tidak ada loop eksplisit yang ditulis.

10Common Pitfalls / Kesalahan Umum

🇬🇧 EN — How We Avoided Them
  1. Mapping container nodes instead of leaves — only leaves carry data. ✓ Avoided
  2. Missing maxOccurs="-1" — would emit only one <Item>. ✓ Avoided
  3. Quote-escaping bugs in Message shapes — most common silent bug. ✓ Avoided
  4. Number-vs-string type mismatch — would yield "55000" instead of 55000. ✓ Avoided
  5. Components in account root — un-auditable. ✓ Avoided
  6. Pushed but not deployed — design push doesn't make it executable. ✓ Avoided
🇮🇩 ID — Cara Kami Menghindarinya
  1. Memetakan node container, bukan field daun — hanya daun yang membawa data. ✓ Dihindari
  2. Lupa maxOccurs="-1" — akan menghasilkan hanya satu <Item>. ✓ Dihindari
  3. Bug escape kutip pada shape Message — bug diam-diam paling umum. ✓ Dihindari
  4. Ketidaksesuaian tipe angka vs string — akan menghasilkan "55000" bukan 55000. ✓ Dihindari
  5. Komponen di root akun — tidak dapat diaudit. ✓ Dihindari
  6. Sudah push tapi belum deploy — push desain tidak membuatnya dapat dieksekusi. ✓ Dihindari
