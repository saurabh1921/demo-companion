Agent Map design
Important call-out on the map: the ttContext repeating block is built in a Message step using process-property values, NOT inside the map. Reason — Map can't drive a repeating XML node off scalar properties cleanly; Message step gives clean control over the three context rows. 
Map outputs:  <salesOrder> + <salesOrderDetail>* only
Message step prepends:  <dsSessionContext> with 3x <ttContext>
Final SOAP body assembled by another Message step that wraps:
  <soapenv:Envelope>
    <soapenv:Body>
      {message-from-map}
    </soapenv:Body>
  </soapenv:Envelope>

Day 2 · 10:55
Agent Fix #1 — WSS Listener Gotcha
Root cause: Boomi's WSS Server is the atom's shared web server. There's no remote endpoint to "connect to" — the listener URL is derived from objectName + operationType. Including connectionId on the <connectoraction> silently prevents the listener from registering on the atom's web server. Deploy reports success; runtime returns 404.
Removed connectionId from the Start step, added hideSettings="true" to match the GUI pattern, redeployed. The WSS connection component itself isn't even strictly needed for the listener — kept it minimal. 
Listener Status (atom UI):

curl now returns: 200 OK + TwiML body ✅

Day 2 · 14:22
Agent Fix #2 — User-Agent header
Boomi's REST/HTTP connectors don't send a User-Agent by default. Cloudflare's bot heuristic flags that as non-browser traffic and serves the challenge page instead of forwarding to origin. Added an explicit header to the QAD operation: 
<properties key="User-Agent"
  value="Mozilla/5.0 (compatible; Boomi-O2C-Integration/1.0)"/>
Diagnostic tip we baked in for the future: a Notify step right after the connector that logs the response. If body starts with <!DOCTYPE html> or contains cdn-cgi/challenge-platform, it's Cloudflare — not the API.
Also flagged for production: ask the QAD network admin to allowlist the atom's egress IP in their Cloudflare config. The header workaround is sufficient for demo but a hardened Cloudflare rule can still block it.

Day 2 · 15:10
Agent Fix #3 — soNbr 8-char cap
Replaced the SO-number generator in SP_Invoke_QAD_with_Retry with an 8-char-safe pattern: 2-char prefix + 6-digit zero-padded modulus of currentTimeMillis: 
// Groovy data process shape
String prefix = props.get('SO_Number_Prefix') ?: 'BO'
String tail   = String.format('%06d',
                  System.currentTimeMillis() % 1000000)
String soNbr  = (prefix + tail).take(8)   // safety cap
// e.g. → "BO780953"
dynProps.put('DDP_SoNbr', soNbr)
Order accepted by QAD. Logged that any prefix coming from PP O2C QAD Config must be 2 chars max.

Agent Error #4
QAD is accepting them. The classifier in SP_Invoke_QAD_with_Retry is producing false positives. The bug: 
// Groovy — naive classification
def isError = response.toLowerCase().contains('error')
Problem: even on a successful maintainSalesOrder, QAD returns warning blocks inside <qcom:dsExceptions> that look like this: 
<qcom:dsExceptions>
  <qcom:temp_err_msg>
    <qcom:err_msgnbr>42</qcom:err_msgnbr>
    <qcom:err_msg>WARNING: Type set to (M)emo</qcom:err_msg>
  </qcom:temp_err_msg>
</qcom:dsExceptions>
<qcom:result>warning</qcom:result>
The element name temp_err_msg contains the literal substring err — substring check matches.
Day 3 · 09:30
Agent Fix #4 — authoritative signal parsing
Switched to a decision matrix based on QAD's actual contract: 
SIGNAL                                            CLASSIFY AS
─────────────────────────────────────────────────────────────
<faultstring>…</faultstring>                       → HARD FAULT
<…:result>error</…:result>                          → ERROR
<…:result>warning</…:result>                        → SUCCESS w/warn
<qcom:temp_err_msg> only (no result tag)            → IGNORE
no fault, no result element                          → SUCCESS
Groovy implementation: 
def faultMatch  = response =~ /<faultstring[^>]*>([^<]+)/
def resultMatch = response =~ /<[^>:]*:?result>(\w+)</

String classification
if      (faultMatch)                       classification = 'FAULT'
else if (resultMatch &&
         resultMatch[0][1] == 'error')     classification = 'ERROR'
else                                       classification = 'SUCCESS'
// 'warning' result and bare temp_err_msg both fall to SUCCESS
Audit success-rate immediately corrected to ~98%. Misclassified historical records re-flagged via a one-off Groovy that re-parsed the stored response bodies in Audit_Disk_Path.

Phase 7 · The Silent TwiML Bug
You
QAD's happy. Audit's right. But customers say they don't get the WhatsApp confirmation on success — only the error-path replies arrive. Boomi log shows HTTP 200 in every case.
Day 4 · 11:00
Agent Error #5
Reproduced. The success-path TwiML differs from the error paths in one important way — it uses a template that includes a placeholder rendered with angle brackets:

Success-path TwiML (broken)

<Response>
  <Message>Order <customer-id> (<so-nbr>) created OK</Message>
</Response>

Error-path TwiML (works)

<Response>
  <Message>Sorry, we could not process your order.</Message>
</Response>
Twilio parses the response body as XML before relaying it to WhatsApp. The literal <customer-id> looks like nested-tag syntax — Twilio's parser fails — Twilio silently drops the response. Boomi sees the 200 from Twilio's webhook acknowledgement and is none the wiser.
Day 4 · 11:24
Agent Fix #5 — TwiML escaping
Three valid options to substitute the angle brackets. Picked square brackets because it reads cleanest in WhatsApp: 
OPTION A · Square brackets   →  Order [customer-id] OK
OPTION B · Curly braces      →  Order {customer-id} OK
OPTION C · HTML entities     →  Order &lt;customer-id&gt; OK
   (Note: in Message-step msgTxt, must be &amp;lt; / &amp;gt;
    due to double-decoding by Boomi)
Final success-path Message step: 
<Response>
  <Message>Order [{1}] ({2}) created OK. Thank you!</Message>
</Response>
<!-- {1} = customer-id, {2} = soNbr -->
WhatsApp confirmations now arrive on every success path. Added the diagnostic note to the project memory so future TwiML-emitting processes don't repeat this.
