Architecture

What was built, and where the posting happens

Three zones: the Abans extract, the Boomi integration, and SAP. Everything in the middle band is a Boomi process step that exists and runs today.

The one design decision that matters most The ledger is written only after SAP confirms the document exists. A failed posting is never recorded as done, so the next run retries it rather than losing it. Reversing those two steps is the easiest way to create silent data loss in an integration like this.

Account translation is a lookup table, not code Four Abans accounts are mapped to demo system equivalents. The extract actually contains eight, so unmapped ones fall through to a fallback account and are flagged in the run — visible as a Fallback badge in the document viewer above. On an Abans SAP system the table is emptied and accounts pass through untouched.

Failure handling

Four situations are handled explicitly

Already posted before

Matched against the ledger and skipped. SAP is never contacted, so a second posting is impossible.

Repeated within the same file

The ledger updates as each document posts, so a second copy in the same batch is caught moments later.

SAP rejects the posting

The reason is captured and the document quarantined. Deliberately not ledgered, so the next run retries it.

A record is corrupt

Quarantined alone with its reason. Every other record in the file continues to post normally.

Where we started

Four manual steps stood between the extract and SAP

  • 1The JSON extract lands on a virtual machine.
  • 2Manual. A person converts it to Excel.
  • 3Manual. The file is moved to a watched directory.
  • 4A custom ABAP program uploads it into SAP.

Described by Abans as costly and slow, taking hours, with no systematic protection against posting the same document twice.

What the data told us

The extracts repeat themselves

10,353Records, 11.6 MB, 8 to 10 July 2025
2,223Distinct documents
4.7×Average repetition
Why this drove the design Posting every record as it arrives would have created roughly 8,130 duplicate financial documents. Deduplication is the core of the solution, not a refinement.

What we built

One Boomi process, from extract to posted SAP document

  • 1Collect the extract, with no manual step.
  • 2Split the run-together JSON into individual documents.
  • 3Check each one against a durable ledger of everything posted before.
  • 4Map it to the accounting document structure SAP expects.
  • 5Post to SAP and read back its confirmation.
  • 6Report posted, skipped and errored, per run.

Open question

One clarification could change the design

The existing ABAP program may apply derivations or validations of its own, beyond simply calling SAP's posting interface. If it does, those rules must be reproduced — otherwise documents could post that today's process would have rejected.

Needs the Abans SAP team. This is the only open item that could materially change the build, and it is worth answering before the next phase is scoped.

Next steps

Three things turn this into a production integration

  • 1Point it at an Abans SAP environment. Company code, chart of accounts, document type and posting periods become the real ones, and account translation is no longer needed. Configuration, not development.
  • 2Confirm the ABAP program's additional logic, the open question on the previous slide.
  • 3Extend to the remaining extracts and full volume. Add customer and vendor line types, cover API0018 and API0023, and move the ledger to a database for parallel posting.
