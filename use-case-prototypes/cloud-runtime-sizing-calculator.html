Boomi Public Cloud Runtime — Sizing Estimator

Each scenario has a processing pattern (Batch / Real-time) and a process mode (General / Low Latency / Bridge) that apply to all its process groups. The estimator shows how many cloud attachments the scenario would take — and which documented ceiling breaks first.

Read me. Boomi does not publish a formula that maps "N processes" to "Y runtime clouds." This tool estimates peak concurrent executions and monthly data volume from your inputs, then compares them to each model's documented per-attachment / per-node ceilings (concurrency, HTTP req/s, queue msg/min, monthly GB, low-latency limits). It reports the binding constraint and required attachments. Treat it as a planning aid — confirm final sizing with your Boomi account team. How the numbers are derived (assumptions & sources)

Scenario type drives the model. Pattern = Batch → General mode only; groups are scheduled and concurrency = runsPerHour × avgSeconds / 3600. Pattern = Real-time → General, Low Latency, or Bridge; concurrency = peakReqPerSec × avgSeconds and the groups also drive HTTP req/s. Low Latency & Bridge add the 30 s worker limit and 5 MB input cap; Batch/General is bounded instead by the 24 h ceiling and 512 MB heap.

Per-model ceilings come from Boomi's public documentation: max simultaneous executions per account (50 Runtime/Option 1, 100 Option 2, 20 Test); HTTP request rate per node (5 / 10 / 20); Atom Queue 7,000 msg/min/node; monthly throughput 1 / 15 / 30 GB. Self-hosted/DCS/MCS have no fixed shared-cloud cap.

Peak concurrent executions = Σ over groups of peakConcurrent × overlap factor. Peak HTTP req/s = Σ peakReqPerSec (real-time scenarios) × overlap. Monthly volume (GB) = Σ docsPerDay × avgDocKB × 2 × working days ÷ 1e6. Queue load = queue-flagged groups' docsPerDay → peak msg/min (×6 burst).

Execution worker nodes apply to worker-run modes only — Low Latency and Bridge (on the public cloud, General cannot be forced onto a worker; that's a private-cloud capability). Each worker provides PER_WORKER_CONC = 20 running executions (+10 queued) and one node's HTTP req/s. Worker-mode ceilings become rateCap = perNodeRate × workers and concCap = min(accountCap, 20 × workers). Documented per-model provisioning is applied and enforced: base Runtime cloud and Test = provisioned on request, max 2; Option 1 = 10; Option 2 = 25; self-hosted/DCS/MCS = set by your hardware. The worker input is capped to each model's max.

Required attachments = max of (concurrency ÷ concCap), (req/s ÷ rateCap), (queue ÷ 7,000), rounded up. Volume overage is a tier/overage flag, not extra attachments. Heap (512 MB) and low-latency 30 s / 5 MB are per-execution constraints — raised as warnings.

Caveats: overlap and queue-burst are modelling choices, not Boomi formulas. Volume metering is approximate. Validate with Boomi before committing spend.
